# Stage 16 — Production Inference and Operations
## Native Serving, Observability, Reliability, and Safe Rollback

**Predecessor:** Stage 15 — Verified Retrieval and Knowledge Plane  
**Successor:** Stage 17 — Controlled Pilot and Production Release  
**Status:** Implemented; PASS — Stage 17 requires explicit approval

**Implementation:** Native C++20 runtime, service control plane, operations harness, and gate

## Purpose

Stage 16 converts an approved model-and-knowledge candidate into a production-like inference service. It provides a versioned API, scheduling, streaming, recurrent-state lifecycle, retrieval integration, policy checks, quotas, observability, deployment controls, canary rollout, rollback, and incident records.

## Scope and non-goals

The stage includes native request/response APIs, authentication and authorization boundaries, schema validation, dynamic batching, streaming, cancellation, state/cache management, model and adapter routing, retrieval/verification integration, rate and resource limits, metrics, tracing, logging, health checks, canary deployment, rollback, and fault injection. It does not authorize a public launch or autonomous external action.

## Request contract

The stable API must expose versioned structured requests and responses:

```text
Request {
    request_id,
    tenant_id,
    model_version,
    adapter_version,
    tokenizer_version,
    input,
    task_schema,
    retrieval_policy,
    tool_policy,
    max_input_tokens,
    max_output_tokens,
    deadline,
    stream,
    trace_id
}

Response {
    request_id,
    model_version,
    output,
    citations,
    uncertainty,
    abstention,
    policy_decision,
    usage,
    latency,
    trace_id
}
```

Plain unstructured output may be supported as a compatibility view, but the canonical response must preserve citations, uncertainty, policy, usage, and trace metadata.

## Request path

```text
request
  -> authentication and tenant policy
  -> schema and budget validation
  -> tokenizer/version check
  -> retrieval and memory policy
  -> scheduler and admission control
  -> CCT/Transformer/hybrid runtime
  -> structured-output and citation verification
  -> safety/policy post-check
  -> audit record
  -> response, stream, or safe abstention
```

No request may bypass validation because it is internal, high priority, or generated by another model. Any approved exception must be explicit, logged, and tested.

## Required implementation

| Component | Implementation | Contract |
|---|---|---|
| API server | Native HTTP/gRPC or audited native binding | Versioned schemas and errors |
| Auth/policy | Identity, tenant, role, and task authorization | Deny by default |
| Scheduler | Dynamic batching and admission control | Deadlines and fairness are explicit |
| Streaming | Token/event streaming, cancellation, backpressure | No orphaned state or resource leak |
| Runtime | CCT, Transformer, hybrid, adapter, and tokenizer routing | Model identity is traced |
| State/cache | Recurrent-state lifecycle and cache quotas | Tenant isolation and reset semantics |
| Retrieval | Stage 15 query/verification path | Evidence policy is enforced |
| Output guard | Schema, citation, policy, and uncertainty checks | Invalid output is rejected or abstained |
| Observability | Metrics, traces, structured logs, health | Sensitive data minimization |
| Reliability | Timeouts, circuit breakers, retries, graceful degradation | Failure modes are bounded |
| Deployment | Versioned images/binaries, canary, rollback | Release identity is immutable |
| Security | Secret isolation, encryption, network/filesystem policy | No unauthorized external action |

## Performance and SLO contract

Initial targets are proposal targets and must be calibrated after measurements:

| Metric | Pilot target |
|---|---:|
| Interactive first-token p95 | ≤ 1.5 seconds at declared prompt size/hardware |
| Streaming inter-token p95 | ≤ 150 ms at declared load |
| Batch throughput | Declared documents/tokens per minute with quality held constant |
| Availability | 99.5% for pilot, excluding planned maintenance |
| Rollback | Prior valid version restored within 10 minutes |
| State memory | Within declared per-request and per-tenant quotas |
| Error rate | Below declared service and safety thresholds |

Targets must be reported with queue time, compute time, retrieval time, verification time, p50/p95/p99 latency, batch size, input/output token counts, hardware, and concurrency. Averages alone are insufficient.

## Cache and state policy

CCT’s recurrent state must be explicit: when it is created, updated, reset, persisted, encrypted, evicted, or deleted. A state cannot cross tenants or users unless a documented, authorized workflow permits it. Cache keys must include model, tokenizer, adapter, policy, tenant, and relevant retrieval/index versions. A stale or mismatched cache must be rejected rather than reused silently.

Modern serving research identifies dynamic KV-cache memory as a critical throughput constraint for attention systems [1]. CCT must measure its own recurrent-state and cache behavior against the matched Transformer control; asymptotic claims do not replace load testing.

## Evaluation harness

The harness must provide:

1. schema, authentication, tenant, and authorization tests;
2. dynamic-batching correctness and fairness;
3. streaming, cancellation, timeout, and backpressure tests;
4. recurrent-state reset, persistence, eviction, and tenant-isolation tests;
5. model/tokenizer/adapter/cache version mismatch tests;
6. retrieval, citation, verification, and abstention integration;
7. latency/throughput/queue/memory curves over load;
8. resource exhaustion and denial-of-service tests;
9. dependency and checkpoint supply-chain validation;
10. network/filesystem/secret isolation tests;
11. canary, rollback, and failed-deployment tests;
12. observability completeness and sensitive-log redaction;
13. deterministic replay of selected requests;
14. fault injection for worker, storage, network, and verifier failures;
15. comparison against CCT-only, hybrid, and Transformer serving paths.

## Mandatory gate checks

| Check | Pass condition |
|---|---|
| API contract | Valid and invalid requests produce versioned, deterministic behavior |
| Authentication | Unauthorized and cross-tenant requests are denied |
| Scheduler | Batching preserves per-request outputs and deadlines |
| Streaming | Cancellation and backpressure release resources safely |
| State isolation | No cross-tenant/user state or cache leakage |
| Versioning | Model/tokenizer/adapter/index mismatches fail closed |
| Latency | Declared p50/p95/p99 targets meet pilot thresholds |
| Throughput | Sustained load is measured with quality preserved |
| Reliability | Timeouts, circuit breakers, retries, and degradation behave as specified |
| Security | No host execution, secret exposure, network bypass, or unreviewed action |
| Auditability | Input, model, retrieval, verifier, policy, response, and error traces exist |
| Canary | New release can be shadowed and compared before user exposure |
| Rollback | Failed release returns to prior valid version within target |
| Regression | Prior Stage 0–15 gates remain green |

## Pass/fail transition

Stage 16 passes only when a production-like service meets the declared pilot SLOs, isolates state and tenants, produces complete traces, survives fault injection, and demonstrates tested canary/rollback behavior. A `PASS` authorizes Stage 17 shadow and limited-pilot preparation.

A `FAIL` requires service, security, performance, or rollback remediation. A `BLOCKED` result is valid if deployment infrastructure, authentication, or monitoring ownership is unresolved.

## Deliverables

The stage must deliver native serving runtime, API schemas, scheduler, streaming path, state/cache manager, auth/policy integration, observability schema, deployment configuration, load/fault harness, canary/rollback automation, service model card, native tests, gate executable, and CI command.

## Implemented gate scope

The native implementation provides a versioned request/response binding, authentication and tenant/role authorization, deny-by-default external-action and tool policy, dynamic batching with deadline admission, streaming cancellation and backpressure, tenant/user-isolated recurrent state, versioned response caching, state quotas and TTL eviction, CCT/hybrid/Transformer-control routing, Stage 15 retrieval and grounded-answer verification, structured latency and throughput metrics, p50/p95/p99 SLO reporting, circuit breaking, fault injection, redacted audit traces, canary shadow comparison, failed-promotion blocking, and prior-release rollback.

The Stage 16 unit executable and formal gate are wired into `ci-stage16`, which chains all prior Stage 0–15 checks before the Stage 16 tests and 15-check operations gate. The release record keeps public launch and external actions unauthorized, and Stage 17 requires explicit approval.

## Explicit limitations

A successful local load test does not prove internet-scale availability. SLOs depend on hardware, workload, and deployment topology. Production availability requires on-call ownership, incident response, capacity planning, and change management beyond the model code.
